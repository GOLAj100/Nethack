# Этап 4 — Visual Entity

## Контракт

`engine/visual.py` содержит backend-независимый `Visual` со всеми полями этапа:
позиция, размеры, rotation, material, uv_scale, параметры источника света,
layer, mesh_id, sprite_id, visible, dirty. Дополнительные поля совместимости:
`color`, `opaque`, `tile_id`.

- `x/y/z` — абсолютные мировые координаты минимального угла объекта.
- `width/depth` — размер footprint по X/Y, `height` — высота по Z.
- `rotation` — радианы вокруг центра footprint. Размеры описывают текущий AABB;
  при повороте прямоугольной мебели на 90° width/depth меняются местами.
- Слои: 0 пол, 1 стены/закрытые двери, 2 мебель/декор, 3 предметы/трупы,
  4 существа, 5 эффекты/светильники.
- `sprite_id` сохраняет существующие идентификаторы глифов/процедурных спрайтов.
- `mesh_id=None` зарезервирован под объёмные модели. Метаданные света готовы,
  но новая система динамического освещения этим этапом не включается.

## Менеджер

`engine/visual_manager.py`: `add`, `remove`, `get_by_layer`, `get_at`,
`mark_dirty`, `clear_dirty`, `iter_visible`.

ID монотонные, не переиспользуются. `get_at` возвращает верхний видимый объект,
содержащий точку; размеры учитываются, верхние границы исключены.
Порядок выдачи: `(layer, z, y)` со стабильным порядком при равенстве.

`VisualCamera` задаёт необязательные мировые bounds
`(left, top, right, bottom, z_min, z_max)` и множество FOV-клеток `(x,y,z)`.
Видимая часть многоклеточной мебели достаточна для включения объекта один раз.
`iter_visible(None)` возвращает все объекты с `visible=True`.

Для прямого изменения Visual после `add` нужно вызвать `mark_dirty(id)`, чтобы
обновить пространственный индекс и инвалидировать кэш. Dirty не сбрасывается
автоматически одним renderer: это не должно скрывать изменения от другого.

## Совместимость с Level

`Level.visual_manager` автоматически создаётся при обращении; перед каждым
чтением менеджер синхронизируется через `game/level_visuals.py`. Ленивое создание
не заставляет строить тысячи Visual для чанков, нужных только игровым расчётам.
Вызовы генерации, размещения, спавна и удаления остаются прежними.

- `tiles` остаётся list-совместимым `TileList`: отслеживаются запись по индексу,
  срезы и замена всего списка. Неизменённые тайлы не сканируются каждый кадр.
- Изменения вложенных словарей дверей, перемещения/повороты мебели,
  добавление/удаление предметов и перемещения/смерть монстров подхватываются
  сравнением небольших сигнатур существующих коллекций.
- Объект Visual обновляется на месте, ID сохраняется при перемещении.
- Абсолютные координаты учитывают chunk_x/chunk_y/world_z, включая отрицательные.
- JSON-сохранения не содержат derived Visual. Старые сохранения и путь
  `Level.__new__()` восстанавливают менеджер автоматически при первом чтении.

Синхронизация **односторонняя**: gameplay → Visual. Изменения Visual не меняют
коллизии/инвентарь игрового мира. Для игровых изменений используются прежние API.

## Рендеринг

- `views.draw()` получает отсортированные Visual из менеджеров видимых чанков.
- `volume.collect_sprites()` использует только Visual слоёв 2–4; оба billboard
  renderer получают этот список. Мебель больше не дублируется по каждой клетке.
- `RayContext` получает снимок VisualGrid один раз на затронутый Level.
  DDA читает массивы стен/пола из снимка, не выполняет sync на каждом шаге.
- Стены слоя 1 и opaque-мебель дают препятствия; слой 0 определяет пол/отверстия.
- GPU rays и software/GPU board используют тот же снимок.
- Отдельная geometry_revision предотвращает пересоздание terrain snapshot и
  загрузку геометрии GPU при обычном перемещении монстра или смене предметов.
- F12 показывает `Visual objects N (active chunk)` в software и OpenGL.

## Проверка и производительность

```text
python -m unittest tests.visual_entity_test tests.gl_pipeline_test -v
python tools/test_stage2_acceptance.py
python tests/visual_benchmark.py
python tests/world_test.py
python tests/furniture_regression_test.py
python tests/graphics_debug_test.py
python tests/render_options_test.py
python tests/vertical_render_test.py
python main.py
```

Baseline acceptance до изменений: GL static 106.6 FPS, rotation 64.0 FPS,
software static 50.1 FPS. Acceptance использует случайный seed и пользовательские
настройки, поэтому отдельный фиксированный benchmark нужен для сравнения.

`tests/visual_benchmark.py`: seed=123, 1280×720, quality=0, три серии по 40
кадров, первые 10 кадров каждой серии исключены, медиана оставшихся 90 кадров.
Звук и чтение пользовательских настроек отключены; измеряется draw + present.

| Режим | До, FPS | Финальный замер, FPS | Изменение |
|---|---:|---:|---:|
| OpenGL static | 125.0 | 123.6 | −1.1% |
| OpenGL rotation | 70.9 | 70.3 | −0.8% |
| Software static | 200.2 | 187.1 | −6.5% |
| Software rotation | 36.8 | 36.6 | −0.5% |

Падение более 10% в этих сценариях не обнаружено. Это локальный benchmark,
а не гарантия для любого оборудования, уровня или графических настроек.

При проверке acceptance один запуск показал rotation 59.7 FPS при пороге >60.
После устранения повторной сборки видимых объектов для billboard-проходов:
static 100.6 FPS, rotation 60.8 FPS, software static 48.0 FPS — тест прошёл.
Финальный запуск после разделения общей и геометрической ревизий:
static **103.6 FPS**, rotation **61.9 FPS**, software static **55.8 FPS** — PASS.
Новые unit-тесты Visual и интеграционные GL-тесты: **18/18 PASS**.

`main.py` запускался отдельным процессом с настоящим окном: отправлены Enter,
F12 и закрытие окна; завершение с кодом 0, без traceback. Наличие счётчика F12
дополнительно проверяется интеграционным тестом игрового renderer.
